Each profile packages a base field/event pair and a full riding/Surf field/event pair, sharing a small resident core and a separate overlay-140 Options module. Registry validation runs in the field module. The core retains object-code bounds, ARM9 event forwarding, and two bounded transition tokens. Packaged CPU checks verified native forwarding with no field, event-module unload, and token recovery after event-module BSS reset. The binary contracts, imports, hook anchors, and base/full variants passed on all four profiles at their listed releases. All four current packages passed full-package checks for conversations, scripts, recall, movement hold, lighting, drawing priority, land riding, Surf handoff, positioning, cycling, terrain, and teardown. A saved-state-derived render fixture checks a nearby NPC's foreground gap across follower bounce frames, and conversation tests check that an accepted follower talk plays the native dialogue-start cue exactly once. The scene tests retain the follower through audited sound-only opcodes, the live `PVPlay` cry child, ordinary Yes/No prompts, and both native dialogue-list display variants, while rejecting unrelated or stale child events. Native services and graphics submission were modeled; no game emulator was run.

The separate Options module passed hook-site and packaged menu checks for button/touch navigation, staged On/Off, Confirm/cancel, save-bit preservation, highlight, markers, and background styling. Pokeweb installer checks passed fresh base/full installation, update from each profile's immediately preceding alpha, enable/disable, removal, full-to-base conversion, and export/reopen. The update checks preserved authored dialogue and exactly one copy of each of the four runtime modules. They also verified that base installs omit mount assets, converted ROMs strip mount payloads without renumbering unrelated file IDs, and unrelated Options text edits survive. Stock and White2Upgrade registry checks exercised packaged lookup, malformed-data rejection, and repeated load/unload cycles. These tests do not establish visual, audible, or live-heap behavior.

The [memory audit](MEMORY-AUDIT.md) measures **788 bytes** of battle-resident follower code/data/BSS on every profile. The cry guard adds 100–104 bytes to the field package and nothing to the battle-resident core. Compared with the preceding core plus resident event bridge, the current design saves **4,664 bytes** in stock White 2, Black 2, and Italian White 2, and **4,884 bytes** in White2Upgrade. The event bridge contributes another 1,464 bytes only if overlay 12 or 36 remains loaded; Options targets overlay 140. Loader metadata, allocator overhead, stack, VRAM, and actual free battle heap are not measured.

The installer accepts data-edited ROMs whose audited hook sites, adapters, and follower archives still satisfy the profile contract. White2Upgrade additionally requires its audited expansion modules. The focused follower suite, TypeScript check, and production build passed; the full web suite passed 1,429 tests with 3 skipped. `cry.mln` also records an earlier unsupported overlay-35 callback before the `PVPlay` child; this release changes the sound path only, so a cold boot must distinguish any earlier scripted recall from a cry-triggered one. Human acceptance remains open for battle transitions, Options, followers, shadows/lighting, land mounts, retail Surf in base, custom Surf in full, and repeated mount/dismount cycles. Cold boot each versioned export with a matching ordinary save; older save states retain earlier loaded code. See the [test map](TEST-MAP.md) and [human checklist](EMULATOR-CHECKLIST.md).
